# P11 PR #33 — Server-side Workflow Execution Worker

## Architecture

The worker runs as a separate process from FastAPI:

`python -m app.bridge.worker`

It polls the durable SQLite Bridge queue, atomically claims one queued execution under `BEGIN IMMEDIATE`, renews a worker lease, executes the DAG in deterministic topological waves, and persists node-level metadata. The Gateway API remains responsive while provider calls run in the worker process.

## Runtime configuration

The worker and Gateway must share the same SQLite database path. Run one or more worker processes against the same database; claims are serialized and lease ownership is checked for state updates.

Required environment variables:

- `PIECS_DATABASE_PATH`: shared persistent SQLite file path.
- `PIECS_SECRET_ENCRYPTION_KEY`: same Fernet key used by the Gateway Vault.
- `PIECS_ASSET_S3_ENDPOINT`: S3-compatible endpoint (Cloudflare R2 endpoint, e.g. account endpoint).
- `PIECS_ASSET_S3_BUCKET`: pre-created bucket name.
- `PIECS_ASSET_S3_REGION`: R2 uses `auto`.
- `PIECS_ASSET_S3_ACCESS_KEY` and `PIECS_ASSET_S3_SECRET_KEY`: R2 S3 credentials.
- `PIECS_WORKER_MAX_CONCURRENCY`: 1–4, default 4.

The Gateway still requires `PIECS_ADMIN_TOKEN` and `PIECS_BRIDGE_TOKEN` for their respective APIs. Do not put these values in frontend variables or image metadata.

Install backend dependencies with `pip install -r requirements.txt`, then start the worker as a separate service/container using the same image, environment, and persistent database volume as the Gateway. Do not run the worker inside a serverless request lifecycle. Ensure only one process owns each SQLite database file at a time per host; use a shared filesystem with SQLite locking semantics only where the platform supports them. For multiple hosts, migrate the queue to a server database before scaling horizontally.

## Object storage

Generated image bytes are written to a private S3-compatible bucket under `piecs/workflow-assets/{asset_id}`. SQLite stores only asset IDs, MIME type, size, model and node status. No presigned/public URL is generated by this worker. The frontend's browser IndexedDB Asset Library remains separate; a future authenticated asset-download/sync API is needed to expose server assets to the browser.

## Execution semantics

- Nodes in the same topological wave run concurrently, capped by `PIECS_WORKER_MAX_CONCURRENCY`.
- A dependent/join wave starts only after every node in its parent wave succeeds.
- A failed node fails the execution and prevents later waves from starting. Sibling calls already in flight in the same wave are allowed to finish.
- Cancellation is cooperative: queued work can be cancelled immediately; running work observes cancellation between waves. An active upstream Gemini request cannot be forcibly stopped by this worker.
- A worker lease is renewed during execution. If a process dies and its lease expires, the next worker marks the execution `interrupted`; it is never automatically replayed because a provider request may already have been billed.
- Execution history stores node status, timestamps, error summaries and asset metadata only. Image bytes remain in R2.

## Capability reporting

`workflow_execution_worker` is true only when R2 settings are present and a worker has reported a recent heartbeat. `workflow_asset_storage` reports whether R2 settings are configured. These checks do not prove the provider credential is valid; the worker will return a sanitized failure if the Vault credential or upstream provider is unavailable.

## Limitations / follow-up

- The current worker executes Gemini image generation/edit nodes using the existing Vault-backed `GeminiImageAdapter`. Other providers and non-image commands are not implemented by this worker.
- Server-side assets are not yet visible in the browser Asset Library; an authenticated asset API is a separate follow-up.
- Webhooks, automatic retries, and forced cancellation of in-flight provider requests are not implemented.
- SQLite is suitable for a single host with a persistent volume. Multi-host deployment should use a server database/queue with equivalent atomic claim semantics.
